# WorkPulse – локальный запуск

Рабочая цепочка: Windows-агент → ASP.NET Core API → PostgreSQL → React UI. Сервер использует ограниченную роль `workpulse_app`, транзакционный контекст организации и проверку области роли. Данные двух демонстрационных организаций синтетические.

## 1. Подготовка

Нужны Windows для агента, запущенный Docker Desktop, Node.js/npm и .NET SDK 10.0.401. SDK можно установить локально, не меняя системный PATH:

```powershell
.\server\setup.ps1
.\database\setup.ps1
.\database\db.ps1 -Action up
.\database\db.ps1 -Action seed
.\server\run.ps1 -Action build
.\server\api.ps1 -Action seed
```

`up` сохраняет существующий volume и применяет Flyway-миграции. Исходные V001–V007 не изменены; V008 добавляет учётные данные и снимки анализа, V009 – защиту завершённых результатов и связь нарушений с актуальным запуском; V010 – график и оценки его соблюдения. Повторный `seed` не сбрасывает существующие пароли.

Демонстрационные организации:

| Организация | ID |
|---|---|
| Север | `10000000-0000-0000-0000-000000000001` |
| Юг | `20000000-0000-0000-0000-000000000001` |

В каждой организации создаются `admin@example.test`, `hr@example.test`, `manager@example.test`, `employee@example.test`. Общий случайный пароль для локальной демонстрации хранится в игнорируемом файле:

```powershell
Get-Content .\tmp\api-demo-password.txt
```

Этот пароль вводится в интерфейсе вручную. Он не включён в исходники. Если файл пароля потерян, повторный `seed` не восстановит пароль существующей записи: не удаляйте файл, ожидая сброса учётных записей.

## 2. Сервер и интерфейс

В первом терминале из корня:

```powershell
.\server\api.ps1 -Action run
```

API: `http://127.0.0.1:5080`; проверка процесса: `/health/live`; OpenAPI в Development: `/openapi/v1.json`. Запуск прерывается, если подключение к PostgreSQL отсутствует или роль БД имеет SUPERUSER/BYPASSRLS. Строка подключения берётся из `database/.env` и не выводится.

Во втором терминале:

```powershell
cd ui-prototype
npm ci
npm run dev -- --host 127.0.0.1 --port 4173
```

Интерфейс: `http://127.0.0.1:4173`. Vite проксирует `/api` на сервер: браузер использует один origin, HttpOnly cookie и CSRF-токен. Роль нельзя переключить кнопкой – нужно войти под другой учётной записью. Для несуществующих или недоступных сотрудников/результатов сервер возвращает 404.

Рабочие разделы: обзор, сотрудники, нарушения, политики, отчёты и настройки. Изменения сохраняются в PostgreSQL. Значения KPI и графики с вымышленными процентами не подмешиваются к реальным данным. `src/App.tsx` хранит предыдущий демонстрационный интерфейс, активная точка входа – `LiveWorkspace.tsx`.

## 3. Подключение Windows-агента

1. Войдите администратором нужной организации.
2. В «Настройки» зарегистрируйте устройство для сотрудника. Для самостоятельного управления обедом используйте сотрудника, связанного с учётной записью `employee@example.test` («Сотрудник API Демо»).
3. Сохраните показанный токен. Он выводится только при создании/ротации; БД хранит его SHA-256-хеш.
4. Подготовьте локальную конфигурацию:

```powershell
Copy-Item .\agent\appsettings.example.json .\agent\appsettings.Local.json
```

В `appsettings.Local.json` замените `token` на выданный токен. Остальные настройки:

```json
{
  "serverUrl": "http://127.0.0.1:5080",
  "token": "ТОКЕН-УСТРОЙСТВА",
  "bufferDirectory": "../tmp/agent-buffer",
  "pollSeconds": 2,
  "idleSeconds": 30
}
```

В третьем терминале из корня:

```powershell
.\agent\run.ps1 -Action run
```

Сборщик работает вручную в интерактивной сессии Windows. Он получает только имя активного процесса и состояние последнего ввода. Polling даёт точность до интервала опроса; содержимое клавиш, заголовки окон, скриншоты и адреса сайтов не читаются. Изменение приложения порождает Focus, ввод – Input, отсутствие ввода – Idle; дополнительно передаются Login/Heartbeat/Logout. `idleSeconds` – порог датчика, а лимит допустимого непрерывного простоя задаёт политика сервера.

События сначала записываются на диск, затем отправляются пакетами. Файлы удаляются только после подтверждения accepted/duplicates. При сетевой ошибке повтор откладывается на 5–60 секунд. Ёмкость – 10 000 событий: при заполнении сбор приостанавливается, доставка продолжает освобождать место. Частично записанный файл сохраняется для проверки, полностью записанный `.pending` публикуется после перезапуска. 401/403 останавливает сбор; данные остаются в буфере.

Для одного буфера разрешён один процесс. Каждое устройство должно иметь отдельный каталог. При ротации токена сначала доставьте очередь, остановите агент и укажите новый пустой каталог: буфер привязан к выданным учётным данным и не должен отправляться от другого устройства. Домен браузера остаётся неизвестным, приложение браузера может классифицироваться как процесс.

## 4. Демонстрационный сценарий

1. Агент автоматически открывает рабочую сессию по Login/Focus/Input при наличии действующей опубликованной политики.
2. Войдите сотрудником, откройте свою карточку, начните и завершите обед. Один обед допускается на одну сессию.
3. Завершите рабочую сессию отдельной кнопкой. Остановка агента и выход из веб-учётной записи сами общую рабочую сессию не закрывают.
4. Войдите HR/руководителем/администратором, откройте сотрудника и нажмите «Анализировать».
5. Проверьте интервалы и нарушения, откройте историю, скачайте CSV.
6. Для поздних событий выполните анализ заново: старый запуск сохранится, текущий журнал использует последний завершённый анализ сессии.

Опубликованная версия фиксируется при начале сессии. Новая версия политики не меняет уже открытую сессию. В API доступны назначения организации, подразделению и сотруднику с приоритетом сотрудник → подразделение → организация; UI назначает политику организации. Срок актуальности сигнала в UI – 120 секунд, в API он задаётся явно (1–86400); это технический параметр, а не норматив организации.

Набор ожидаемых устройств для анализа – устройства, чьи периоды регистрации пересекаются с периодом, плюс устройства событий. Набор фиксирован для одного запуска; отсутствие подтверждения хотя бы одного устройства исключает вывод об общем Idle. Новый/отозванный посреди сессии датчик может дать консервативный Unknown. Активность всё равно учитывается один раз.

Старые фиксированные сессии seed ЛР7 – исторические фикстуры модели; у них публикация политики могла быть позднее начала сессии. Для демонстрации аналитики создавайте новые сессии: доменная проверка не подменяется ради старых фикстур.

## 5. Проверки

```powershell
.\server\run.ps1 -Action test
.\database\db.ps1 -Action test
.\database\db.ps1 -Action validate
.\agent\run.ps1 -Action test
python .\server\tests\api-smoke.py
```

Последняя команда требует Python 3, запущенный API и выполненный `seed-users`; создаёт отдельные синтетические записи и выполняет 29 HTTP-проверок. Данные проверки остаются для просмотра, существующие рабочие записи не удаляются. Проверки БД откатывают свои изменения. Тест агента использует подменённый HTTP-обработчик и не собирает Windows-активность.

Для UI из `ui-prototype`: `npm run check`, `npm run build`, `npm run test:sites`. Упаковка Sites проверяется как статическая сборка; публичного API/развёртывания Sites этот этап не создаёт.

## 6. Остановка и повторный запуск

Остановите агент, UI и API через Ctrl+C в соответствующих терминалах. Затем:

```powershell
.\database\db.ps1 -Action down
```

Volume и данные сохраняются. Для повторного запуска достаточно `database/db.ps1 -Action up`, затем API, UI и агент. Не используйте `down -v` для обычной остановки.

## Границы текущей версии

Коллекции ограничены 1000 строками, истории сессий/запусков – 200; один анализ – 7 дней и 100 000 событий. Это ограничения локальной реализации, не подтверждение проектной нагрузки 5000 сотрудников. В ЛР10 добавлены график, опоздания/ранний уход, KPI, сравнение и PDF/XLSX. Доставка уведомлений и HRM/ERP остаются вне реализованного объёма. Проверки и формулы: [testing/README.md](testing/README.md). Для размещения вне localhost необходимо HTTPS; HTTP разрешён только в локальной демонстрации.

Контракт: [api-contract.md](api-contract.md). Проверки: [lr9-verification.md](lr9-verification.md). Схемы: [design/lr9-models.md](design/lr9-models.md).

Для тестов и покрытия: server/run.ps1 -Action test или -Action coverage; затем server/coverage-summary.ps1. HTTP-прогон: python server/tests/lr10-integration.py. UI: npm --prefix ui-prototype run test:live после HTTP-прогона и запуска UI.


Полное руководство развёртывания ЛР11: [deployment/README.md](../deployment/README.md). Руководство пользователя: [deployment/user-guide.md](../deployment/user-guide.md). Изолированная проверка восстановления: deployment/verify.ps1.
