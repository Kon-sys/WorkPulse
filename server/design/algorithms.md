# Алгоритмы WorkPulse, ЛР8

Источник бизнес-правил: ответы пользователя в чате 12.10.2026. Технические детали детерминизма и покрытия ниже – явно выделенные решения реализации первой версии, а не утверждения исходных лабораторных.

## Сессия и перерывы

`WorkSession.StartFromSignal` принимает Login, Focus или Input. Организация, сотрудник, устройство и ключ события обязательны. `Start` проверяет принадлежность и время публикации политики, фиксирует её версию и текущий отдел. Это создание одной сессии; поиск уже открытой сессии и конкурентная запись потребуют репозитория/транзакции при подключении API. В ЛР7 пересечения сессий дополнительно запрещены ограничением PostgreSQL.

`StartBreak` проверяет, что сессия открыта, время не раньше её начала, нет другого открытого перерыва, предыдущие перерывы закончились и id уникален. Для Lunch дополнительно проверяется отсутствие прежнего обеда. `EndBreak` закрывает текущий перерыв строго после его начала. `End` допускает Manual или Logout, проверяет границы всех перерывов, закрывает открытый перерыв и затем сессию. При ошибке состояние остаётся прежним. Перерыв нулевой длины не допускается.

Окончание графика не является командой End. Сигнал logout устройства в реконструкции лишь сбрасывает состояние этого устройства; команда закрытия общей сессии выполняется отдельно. Иначе выход с одного ПК ошибочно завершил бы работу сотрудника на другом. Ручной режим обеда принят пользователем; автоматический обед не реализован. Rest допускается моделью хранения, но его аналитическая категория/лимит не согласованы: в этой версии он даёт Unknown и не создаёт автоматическое нарушение.

## Построение временной шкалы

Реализация: `ActivityReconstructor.Reconstruct`.

1. Проверить параметры: опубликованная версия совпадает с версией сессии; организация и сотрудник событий совпадают; устройства входят в ожидаемый набор; клиентский ключ, вид и время события корректны. Период анализа начинается со старта сессии и заканчивается минимумом until и закрытия сессии.
2. Сгруппировать события по `(DeviceId, ClientEventId)`. Повторы одного payload удалить; разные payload одного ключа отклонить. Различающееся время получения не меняет смысл события.
3. Отобрать события до конца рассматриваемого периода. Сортировать по OccurredAt, DeviceId, EventKind и ClientEventId. Для событий одного устройства в один момент порядок: Login, Focus, Input, Idle, Heartbeat, Logout. Это стабильное техническое правило разрешения одновременных сигналов.
4. Построить упорядоченный набор границ: начало/конец, времена событий, истечение срока актуальности сигналов, начало/конец перерывов. Все интервалы полуоткрытые `[start, end)`.
5. На каждой границе обновить состояние устройства всеми событиями до неё. Login сбрасывает контекст; Focus задаёт ресурс и активность; Input подтверждает активность и обновляет ресурс, если он передан; Idle подтверждает простой; Logout сбрасывает устройство. Heartbeat продлевает непрерывное покрытие, но после разрыва покрытия не восстанавливает прежнюю категорию или idle.
6. Явный перерыв имеет приоритет: Lunch, AuthorizedAbsence или Unknown для Rest.
7. Иначе выбрать актуальные активные устройства. Побеждает устройство с последним Input; без Input используется время Focus. При равенстве выбирается меньший Guid DeviceId (`Guid.CompareTo`). Наличие активного устройства имеет приоритет над idle других. Не суммировать длительности устройств.
8. `PolicyResourceClassifier` выбирает категорию ресурса по неизменяемой версии политики. Отсутствующий/неизвестный ресурс – Neutral, если активность подтверждена. Отсутствие самой активности – Unknown.
9. Если активных устройств нет, Idle допускается только при актуальном idle всех устройств ожидаемого набора. Неизвестное/неактуальное устройство не позволяет доказать общий простой, поэтому результат Unknown. Ожидаемый набор передаётся вызывающим кодом; нельзя автоматически включать все когда-либо зарегистрированные ПК сотрудника.
10. Соседние интервалы одинаковой категории объединить, даже если менялся ресурс или устройство. Сохранить объединённые ссылки на исходные события `(DeviceId, ClientEventId)`. Итог полностью покрывает период, не содержит разрывов, пересечений и интервалов нулевой длины.

Срок актуальности (`AnalysisOptions.SignalLifetime`) – обязательный положительный параметр до одних суток. В демо он равен 2 минутам; промышленное значение согласуется с частотой агента. Событие достаточно актуально, пока `time - OccurredAt < SignalLifetime`. Heartbeat, пришедший точно на границе, поддерживает непрерывность; пришедший позднее сбрасывает старую доказательную информацию. Это правило предотвращает бесконечное продолжение последней активности при потере связи.

Текущее ядро работает с полным набором событий рассматриваемой сессии и не является потоковым накопителем. Оценка сложности: сортировка `O(E log E)`; обход границ `O((E+B) × (D log D + B))`, где E – события, D – устройства, B – перерывы. Для первой учебной версии это приемлемо; большие объёмы и инкрементальные пересчёты потребуют отдельной оптимизации.

## Обнаружение нарушений

Реализация: `ViolationDetector.Detect` и `ExceedsLimitSpecification`.

Для каждого непрерывного интервала выбирается правило: Idle → IdleLimit, NonTarget → NonTargetLimit, Lunch → LunchLimit. Для прочих категорий правило отсутствует. При `Duration > Limit` создаётся одно нарушение с полным началом и концом интервала и использованным лимитом. Ровно лимит не является нарушением. AuthorizedAbsence, Neutral, Productive и Unknown не создают нарушений. Это подсчёт по готовой шкале; автоматическое подтверждение HR и отправка уведомлений не реализованы.

## Пересчёт и происхождение данных

`AnalysisService.Analyze` вызывает реконструктор и детектор, создаёт новый AnalysisRun с Guid, tenant/session/policy, версией алгоритма, сроком актуальности и границами, затем вызывает `IAnalysisRunStore.Append`. При поздних событиях вызывается Analyze повторно с новым полным набором; старый запуск не изменяется. Автоматического планировщика пока нет. Политика остаётся версией исходной сессии: изменение новых политик не подменяет историческую классификацию.

Источники интервалов используют клиентские составные ключи. Будущий PostgreSQL-адаптер должен сопоставить их с `activity_events.id` при записи `interval_sources`. Отдельных миграций ЛР8 не создаёт. SignalLifetime пока хранится в объекте AnalysisRun; его долговременное хранение и совместимость с таблицей analytics_runs должны быть решены при реализации адаптера. Дедупликация нарушений между запусками и выбор актуального запуска для UI также относятся к этому этапу интеграции.

## Реально применённые паттерны

| Паттерн / подход | Где используется |
|---|---|
| Aggregate Root | WorkSession защищает состояние и коллекцию перерывов |
| Strategy | IResourceClassifier / PolicyResourceClassifier заменяют способ классификации |
| Specification | ExceedsLimitSpecification отделяет проверку строгого превышения |
| Ports and Adapters | IAnalysisRunStore и InMemoryAnalysisRunStore разделяют сценарий и способ хранения |
| Immutable Snapshot | PolicySnapshot копирует справочник правил, исключая изменение принятой версии |

Это набор применённых решений, без фиктивных Observer/Factory/Singleton ради диаграммы.
